# Accounts and progress sync — design (sub-project 1 of 3)

Date: 2026-10-17. Status: draft for review.

## Goal

An adult can sign in from the parents' panel so that the children's progress, stickers and profiles follow them across devices. Other families will use the app too, so child data is kept minimal and the privacy work (sub-project 2) is a hard gate before public launch.

## Decisions already made

| Question | Decision |
|---|---|
| Who uses accounts | Other families too (not only Fran's). |
| Backend | Managed: Supabase (Postgres + Auth), EU region. |
| Login | Email + 6-digit code, no passwords. Google/Apple may come later on top. |
| Offline divergence | Merge by counters (highest value wins), never "latest copy wins". |
| Login required? | No. Optional. The app keeps working with no account, exactly as today. |
| Existing local profiles | On first sign-in the adult chooses, per local profile, "same child as X in the account" or "add as new". |

## Sub-project split

1. **Accounts and sync** (this document).
2. **Privacy and consent**: privacy policy page, consent wording, "download my data", "delete my account and all data". Required before other families use the feature. Everything here is designed so it fits without changing the data model.
3. **Hosting and operations**: https hosting, email sender, rate limits, backups.

Later and out of scope here: social login, sharing a child between two adults, teacher view, syncing the parent's recorded voice clips, push notifications.

## Principles

- **Optional and offline-first.** No sync code runs unless the adult signed in. A tablet that never signs in behaves as it does today. If the sync config is absent, the sign-in UI is hidden.
- **Minimal child data.** Only a nickname, the progress counters, stickers and Leo's unlocked groups. No child email, no analytics, no device identifiers, no third-party scripts (CLAUDE.md rule stays: no tracking, ads or data sharing).
- **The database enforces ownership.** Row Level Security, not client code, decides who reads what.
- **No bundler, no SDK.** Plain `fetch` against Supabase's auth and REST endpoints.
- **Merging is a pure function** with its own tests.

## 1. Data model (Supabase)

Supabase Auth owns accounts (`auth.users`). One table:

```sql
create table public.child_profiles (
  id          uuid primary key,                       -- generated by the client (crypto.randomUUID)
  owner       uuid not null references auth.users(id) on delete cascade,
  name        text not null check (char_length(name) between 1 and 40),
  kind        text not null check (kind in ('reader','pre')),
  data        jsonb not null default '{}'::jsonb check (pg_column_size(data) < 200000),
  version     integer not null default 1,
  updated_at  timestamptz not null default now()
);
alter table public.child_profiles enable row level security;
-- select / insert / update / delete: only when owner = (select auth.uid())
-- insert and update also require owner = (select auth.uid()) in WITH CHECK
```

- At most 8 child profiles per account (enforced by a trigger), and `data` is capped at 200 KB, so one account cannot be used to store arbitrary data.
- `version` supports optimistic concurrency (section 3).
- The migration lives in `supabase/migrations/` and is applied by Fran in the Supabase SQL editor (or the CLI).

### What goes in `data` (synced)

| Field | Merge rule |
|---|---|
| `stats` (map item key → `{ok, fail, …}`) | union of keys; each numeric field = max of the two sides |
| `total`, `stickers` | max |
| `pre` (`{es, ca}`, Leo's unlocked group) | max per language |
| `level` | from the side with the larger `modAt` (it is a current position, not a counter: a parent may lower it on purpose) |
| `name` (nickname, also in the `name` column) | from the side with the larger `modAt` |
| `modAt` (ms since epoch, set on every progress-changing save) | max |

Not synced (device-specific or large): `sound`, `voiceURI(s)`, `rate`, `theme`, `sessionLen`, `world`, `mode`, `lang`, `upper`, `upperMigrated`, `progress`, and the IndexedDB voice recordings. They are never read from or written to the server.

Properties the merge must satisfy (tested): commutative, associative, idempotent, and never decreasing any counter.

## 2. Authentication

Supabase email OTP, using the REST endpoints directly (names to be re-checked against the current Supabase docs when the plan is written):

1. `POST /auth/v1/otp` with `{email, create_user: true}` → Supabase emails a 6-digit code (the email template must include `{{ .Token }}`).
2. `POST /auth/v1/verify` with `{type: 'email', email, token}` → returns `access_token`, `refresh_token`, `expires_in`, user id.
3. `POST /auth/v1/token?grant_type=refresh_token` when the access token is near expiry.
4. Session stored in `localStorage['leemos-auth']`. Sign out removes it (local progress stays on the device).

The sign-in screen requires a checkbox: "I am the parent or guardian and accept the privacy policy" (policy text and link come from sub-project 2; until then the link is a placeholder and the feature is not announced publicly).

Config in `src/data/sync.config.json`: `{ "url": "", "anonKey": "" }`. The anon key is public by design (protected by RLS). Empty = feature hidden.

## 3. Sync protocol (`src/sync.js`, loaded with dynamic `import()` only when signed in or when the adult opens sign-in)

Local profile list entries get an optional `rid` (the remote uuid). `cleanProfiles` must preserve it.

**Pull-merge-push for one profile:**
1. `GET /rest/v1/child_profiles?id=eq.<rid>` → remote `{data, version}`.
2. `merged = merge(local, remote.data)` (pure function, `src/merge.js`).
3. `PATCH …?id=eq.<rid>&version=eq.<v>` with `{data: merged, name, version: v+1}` and `Prefer: return=representation`. An empty result means another device wrote first: go to step 1 (up to 5 tries, then try again at the next trigger).
4. Apply `merged` to local state and save.

A new profile is created with `POST` (client-generated uuid).

**Triggers:** app start (if signed in), right after sign-in, 5 s after the last progress change (debounced), and `visibilitychange`→hidden / `pagehide`. Offline or any network error leaves the profile "dirty" and the next trigger retries; the state is a whole document, so no operation queue is needed. Token refresh happens transparently before a request.

**Service worker:** must not cache or intercept requests to the Supabase origin. `sw.js` handles same-origin only (to be confirmed at plan time; add a test if it needs changing).

## 4. First sign-in on a device (linking)

After a successful code:
1. Load the account's profiles (`GET /rest/v1/child_profiles`).
2. Account has none: create one remote profile for every local profile (each gets a new `rid`), push.
3. Account has some: for each local profile without a `rid`, ask the adult "Is *Elsa* (on this tablet) the same child as: [account profile 1] / [account profile 2] / No, add as a new child". Linking runs the normal pull-merge-push, so progress from both sides is kept.
4. Account profiles not linked to any local profile are added to this device automatically (created locally from the remote data, with their `rid`).
5. **Different account on the same device:** the user id of the last sign-in is remembered. If the new user id differs, every local `rid` is dropped first, so profiles of account A are never uploaded into account B without the same linking question.

## 5. What the adult sees (parents' panel, "Para papá y mamá")

- Signed out: a "Save my progress on all my devices" block with the email field, then the code field, then the consent checkbox.
- Signed in: the email, "Synced 2 min ago" (or "Not synced yet: no connection"), "Sign out". "Download my data" and "Delete my account" are added by sub-project 2.
- The linking questions appear as a simple dialog.
- All texts in `i18n.es.json` and `i18n.ca.json` (parity is tested).
- The child never sees any of this. Leo's profile never shows it (parents switch profiles from their panel, as today).
- Nickname guidance under the profile name field: "Use a nickname, not the full name."

## 6. Security and privacy notes

- RLS is the access control. The anon key in the repo only identifies the project.
- Tokens in `localStorage` are exposed if the app suffers XSS. The app has no user-generated HTML and no third-party scripts (Google Fonts is a stylesheet; self-hosting it is an existing pending item).
- OTP brute force and email abuse are limited by Supabase's auth rate limits, configured in sub-project 3.
- A custom email sender is required for real use (Supabase's built-in sender is capped at a handful of emails per hour). Configured in sub-project 3.
- Region: EU. Supabase's data processing agreement is accepted by Fran as the account holder.
- No logging of progress data on the client beyond what exists today.

## 7. Testing

- `tests/merge.mjs`: unit and property tests of the merge (commutative, associative, idempotent, counters never decrease, `level`/`name` follow `modAt`, missing or malformed fields, `__proto__` keys in `stats`).
- `tests/sync.mjs`: protocol against a fake fetch server: pull-merge-push, a version conflict then retry, offline then recovery, expired token then refresh, bad code, sign-out keeps local data, different account on the same device drops `rid`s, the service worker ignores the Supabase origin.
- `tests/smoke.mjs`: the panel with and without config (hidden when empty), the linking dialog, no network traffic when never signed in, i18n parity.
- `scripts/check-rls.mjs`: runs against a real Supabase project with two test users (created with the service key, which stays in `.env` and is never committed) and verifies that user B can neither read, update nor delete user A's rows, and that the profile and size limits hold. Run by Fran after applying the migration.

## 8. Failure modes the design must handle

- Two devices write at the same moment (version conflict).
- The tablet is offline for days, then reconnects.
- The refresh token is revoked or expired: the adult is asked to sign in again; local data is untouched.
- The remote row is malformed or from a newer app version: ignore unknown fields, never crash, never delete local data.
- Clock skew affecting `modAt` (only `level` and `name` depend on it).
- The adult signs in with the wrong email: nothing is uploaded before the code is verified, and signing out leaves local data intact.
- Account deleted elsewhere (sub-project 2): the next sync gets 401/404; the device keeps its local data and shows "signed out".
